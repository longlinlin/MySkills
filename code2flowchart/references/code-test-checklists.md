# 从代码流程到 UT 与时序集成测试

## 范围与来源

只用于选定 C/C++ 代码的流程图追溯、单元测试，以及接口协作和时序集成测试。不包含通用架构图、安全扫描、MISRA/CERT 审查、资源盘点、客户发布与审批流程。

提炼自用户提供的《UVP 软件单元验证清单》第 6 章，以及《ITP 软件集成测试清单》第 2、4、7 章。它们是项目资料，不是本技能已验证的行业标准或所有项目的强制要求。未复制原项目的客户名、版本截止日期、角色审批规则和交付平台要求。

| 来源内容 | 纳入方式 | 不直接照搬的部分 |
| --- | --- | --- |
| UVP：需求与故障注入、分支覆盖、执行证据 | 转为 UT 用例设计和验收检查 | 不把路径枚举数当成覆盖率；不把项目的 100% 目标说成已经达成 |
| UVP：用例 ID、代码版本、失败回归 | 保留需求/函数/路径/用例/日志的追溯关系 | 不自动创建 Git tag，不绑定专有问题平台 |
| ITP：接口、动态行为、功能时序 | 明确真实组件边界、事件链、时间判据和观测点 | 不把“所有依赖 mock”用于真实组件间的集成链 |
| ITP：环境、失败记录、选择性回归 | 记录阻塞原因、执行结果、修复及回归范围 | 不采用内部版本免记录的规则；无证据不能报 PASS |

## 先确认事实与边界

- 读取被测函数、真实调用点、头文件、宏与活动编译配置；`.analysis.json` 和 `.paths.md` 是辅助材料，不能覆盖源码事实。
- 标明需求或设计依据。只有源码时，可以生成基于实现的测试草案，但不能声称已验证需求正确性。
- 明确测试层级、选中范围、输入、输出、全局状态、硬件依赖、被测版本和环境。缺失信息写 `TBD`，不要从函数名推测接口签名或时限。
- 先审查路径可行性：循环展开的候选路径可能矛盾或不完整。不可行、重复、无法确认的候选分别记录处置原因；额外边界用例无需与候选路径一一等量。
- 流程图边编号只在同一版图内可追溯；源码或图修改后重新映射，不能把旧边号当成永久需求 ID。

## 单元测试

### 设计检查

| 检查项 | 落地要求 |
| --- | --- |
| 正常路径 | 由接口契约与源码确定输入、输出、返回值和可观察副作用 |
| 等价类 | 按参数类型、有效范围及无效类别划分，不能按路径在列表中的位置分配 |
| 边界值 | 针对真实比较符、计数与缓冲长度选取阈值前/等于/后的可表示值；不制造类型溢出或未定义行为 |
| 多参数组合 | 覆盖实际存在的参数约束与关键组合，写清选取依据；不默认穷举所有组合 |
| 分支与循环 | 核对判断结果、零次/一次/多次、最后一次成功、耗尽与提前退出；只选源码允许的情况 |
| 故障注入 | 对源码可处理的外部错误、超时、资源失败设计输入，不凭空要求不存在的错误处理 |
| 依赖隔离 | 按真实声明 stub/mock 外部调用；显式设置和复位全局/静态状态，不 mock 被测函数本身 |
| Mock 断言 | 记录参数、返回序列、调用次数与有要求的顺序；未知签名留待补充，不能一律返回成功 |
| 清理行为 | 检查锁、队列、缓冲、状态与资源释放，确保用例不依赖前一用例留下的状态 |

用例至少包含：用例 ID、函数 ID、源码版本、需求/设计依据、流程图边序列、设计方法及理由、输入、初始状态、mock 设置、动作、具体预期值与副作用、执行状态、日志和缺陷引用。

未提供函数 ID 时，生成器使用 `LOCAL_Fxxx` 作为草稿标识，不冒充项目正式编号。项目采用源清单命名时，可使用 `MCU_<FuncID>_UTxxx`；已有 `MCU_` 前缀时不要重复添加。现有 `--project-prefix` 仍可配置编号。

### 覆盖率与执行证据

- 代码分支覆盖率来自实际编译、运行后的覆盖率工具报告；记录工具及版本、编译配置、统计范围、已覆盖/总分支数和报告路径。
- 静态流程图不能证明实测覆盖率，路径数量、用例数量及测试程序退出码均不能替代该报告。
- 用户采用源清单的目标时，将分支覆盖、选中用例执行率和通过率分别设为 100%；未确定目标或统计分母时写 `TBD`。
- 执行率 = 实际执行用例数 / 选中用例数；通过率 = 通过数 / 实际执行数。没有分母或没有执行时写 `N/A`，不能写 100%。NE、SKIP、BLOCKED 不算已执行通过。
- 编译错误、环境错误和测试代码自身错误属于阻塞，不等同于被测代码断言失败；修复后重跑相关用例并保留两次记录。
- 生成的 `.ut.c/.ut.cpp` 是草稿，不是已经验证可编译的项目测试。未补入真实调用和断言前保留跳过保护；框架退出码为零也可能包含跳过用例，必须检查结果数量。

## 接口与时序集成测试

集成测试验证选定真实组件如何协作，时序是其中一类验证内容，不等同于画 UML 时序图。不能仅凭多个调用框就声称集成关系成立。

### 集成边界

- 列明边界内的真实模块、入口、出口、调用/回调、队列、信号量、共享状态或中断事件，并给出源码或设计依据。
- 边界内被验证的协作链保留真实实现；仅隔离边界外依赖，故障注入点需明确。若协作模块全部被 mock，只能作为隔离的交互测试，不报告为真实集成验证。
- 可按已确认的依赖关系由底向上集成，但不能把原项目的固定顺序套到所有项目。
- 主机测试、SIL、PIL、HIL 按实际环境标注。硬件相关看门狗、中断及外设真实时序若需要硬件确认，主机 mock 的结果不能代替。

### 事件与时间判据

| 项目 | 必须明确的内容 |
| --- | --- |
| 事件链 | 触发输入、参与组件、每个可观察事件、完成或错误出口 |
| 先后关系 | 有依据的调用顺序或 happens-before；并发事件允许偏序，不强制虚假的全局顺序 |
| 观测信息 | 事件 ID、任务/中断上下文、关联 ID、时间戳、时钟来源、单位和分辨率 |
| 预期时间 | 超时/周期/响应上限来自需求、设计或已确认配置；缺失时写 TBD，不从一次测量反推验收阈值 |
| 时钟一致性 | 使用可比较的单调时钟；跨设备需同步或说明误差，处理计数器回绕，tick 转时间需已知频率 |
| 断言 | 如 A 先于 B、B 恰好出现一次、`t_done - t_trigger <= deadline`，以及实际错误恢复结果 |
| 边界与扰动 | 按源码选择阈值前/等于/后、队列满、事件丢失/重复、外部失败、抢占、取消等场景 |
| 超时竞态 | 明确截止时刻同时到达的事件如何判定；未定义时记录歧义，不编造“等于阈值必成功” |

可用可控时钟测试逻辑超时；该结果不等于实机响应时间。重复 `sleep`、单张截图或一次手工计时都不足以证明严格时序。没有明确要求的顺序不额外限制。

## 输出与状态

以下是 AI 按需撰写的文档，不是新增 CLI 参数，也不是脚本自动执行硬件测试的承诺：

| 文档 | 最少内容 |
| --- | --- |
| `<scope>.it.md` | 真实集成边界、依赖隔离、接口矩阵、场景与故障注入、入口条件、判据、回归范围 |
| `<scope>.timing.md` | 事件链、顺序约束、时间上限及依据、观测点、时钟、输入与具体断言 |
| `<scope>.test-traceability.md` | 需求/代码位置、图版本与边号、UT/IT ID、待测判据、证据链接及缺口 |
| `<scope>.test-result.md` | 实际运行的版本、配置、工具/硬件、命令、时间、通过/失败/未执行数量、实测值、日志与缺陷关联 |

只生成用户请求的文档，不自动补一整套流程文档。尚未执行时，可在设计文档中列出 NE，不生成看似已经完成的实测报告。

状态使用 `PASS`（实际执行且符合具体判据）、`FAIL`（执行后违反判据）、`NE`（未执行）、`BLOCKED`（环境/测试代码阻塞）、`SKIP`（有理由跳过）。图的 `.self-check.md` 仍使用自己的 `PASS/PARTIAL/FAIL`，不可混用为测试结果。

回归依据影响范围决定。采用用户清单的项目策略时，模块任一用例失败后重跑该模块全部用例，并复核受影响的跨模块与时序链。无执行能力时交付设计、命令建议和缺口，不编造日志、覆盖率或实板结论；未经授权不安装依赖、上传源码、操作硬件、创建 tag 或提交推送。

## 最终自查

- [ ] 每条 UT/IT 有真实源码或需求依据，未知宏和配置已说明。
- [ ] UT 的隔离边界和 IT 的真实组件边界不同且明确。
- [ ] 输入、预期值、时间判据可执行，缺失依据保持 TBD。
- [ ] 图边序列与当前图版本一致，候选路径已审查可行性。
- [ ] 未完成骨架保持跳过，NE/SKIP/BLOCKED 未被计成 PASS。
- [ ] 覆盖率、执行率、通过率与实测时序分别列出依据和分母。
- [ ] 失败、修复和回归记录可追溯；没有实测时明确写未执行。

骨架跳过机制参考：[GoogleTest GTEST_SKIP](https://google.github.io/googletest/reference/testing.html#GTEST_SKIP)、[Unity TEST_IGNORE_MESSAGE](https://github.com/ThrowTheSwitch/Unity/blob/master/docs/UnityAssertionsReference.md)。
